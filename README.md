# FSSAI Online — Portal Frontend (mockup)

React + Vite + Tailwind SPA with a small Node API (auth, document upload/verification) backed by PostgreSQL.

## Run

```bash
npm install
npm run dev
```

Opens at http://localhost:5173. `npm run build` produces a production bundle in `dist/`; `npm run preview` serves it locally.

## Notes

- Auth: email + password registration/login (`/api/auth/*`), scrypt salted hashes, server-side sessions in an HttpOnly cookie, failed-login throttling. No 2FA yet.
- Access: the server listens on the VPN interface only (`vite.config.js`) and accepts only the `fssai.photovault.live` host; HTTPS is terminated by Caddy on the VPN master, which must send `X-Forwarded-Proto: https`.
- Config: `config/database.json` (PostgreSQL + repo-relative `storageDir`), `config/llm-provider.json` (vision model), `config/document-types.json` (per-document questions).
- Application flow (`/dashboard/apply`, the first screen after login): photo-first (ID + address proof, read by the vision model to pre-fill details), then tap-first intake, licence summary, details, documents, auto-filled Form A/B, then ready for submission. **Everything is worked out on the server**; the browser only shows what it is sent (`app.intake`: the current question, summary rows and result; `app.plan`: licence, fee, fields, documents, readiness, form).
- Intake engine (`server/intake/`): the rules are data, in `config/intake/graph.v2.json` (licensing by FoSCoS Kind of Business, 2026 eligibility table), run by the engine in `server/intake/engine/`. Both are built and released in `~/fssai-intake-lab` and copied here with `scripts/intake/sync-from-lab.sh`; don't edit them here. `node scripts/intake/check.mjs` validates the graph, runs the scenario cases and walks every tap path (~246,000, ~3 min; `--quick` skips the walk). Each application records the graph version it was answered under; an unfinished one from an older version restarts its intake.
- Plan (`server/intake/plan.js`): licence, fee and documents come from the graph result. Its documents (FoSCoS list, March 2021 order) map to upload types in `config/intake/documents.json`; the rest (mostly letterhead declarations) are prepared with the applicant on the filing call. Payments charge the graph's fee.
- Typed answers (`server/intake/interpret.js`) only pick among the current question's options: state names and amounts ("80 lakh a year") are read by code; otherwise (1) reviewed records (`config/intake/records.v2.jsonl`), (2) CLM when it is at least 80% confident (`config/intake/intake.json`; start it with `~/fssai-intake-lab/testbed/clm-up.sh`), (3) the 10.8.0.5 model for signed-in users, cached in `intake_answer_cache`, (4) clarifying taps with the best guesses first. Spark reviews every interpreted answer silently. Personal details are redacted first. Typed answers, silent reviews and "Is this right?" ratings go to `intake_events`.
- Landing chat: `POST /api/intake/{preview,resume,answer,undo,restart,rate}`, public, 60 requests a minute per IP, records and CLM only (never the model). The conversation is stored in `intake_sessions` once the first answer is accepted, and the first application after sign-up takes it over.
- Operations console (`/ops`, ops team and admin only): a case opens when an application's payment goes through (`cases`, in the payment transaction). The queue shows status, flags (missing documents, documents to review, password-protected PDFs, expert handover, results rated wrong, test payments) and the owner; members take cases and transfer them to each other. Every change is logged in `case_events`. Ops accounts can't use the customer dashboard or APIs, and their sessions last 12 hours. Accounts are managed on the CLI only: `node scripts/ops.mjs add --email … --name … [--role ops|admin]`, `list`, `deactivate`, `activate`, `role`, `reset-password` (passwords are generated and shown once). `config/ops.json` holds the company mobile number used as FoSCoS's secondary number in filing sessions. The company is a consultant: the customer files and declares, with ops filling FoSCoS live in a screen-share session.
- Dashboard: `/dashboard` sends a user with a completed application (status `ready`) to the Dashboard and everyone else to My Application. Nav: Dashboard, My Application, Premises, Document Vault, Support. All pages read the user's real application and documents. Support saves "Talk to an expert" requests in `support_requests` (topics in `src/lib/supportTopics.js`). Mock-data screens (AI Assistant, Notices, Registrations & Licences, Payments, old dashboard) are archived in `src/archive/`, and their old URLs redirect to the dashboard.
- Landing page: the hero chat runs the same tap-first questions and licence rules in the browser (no login, no model). Answers are kept in `localStorage` and replayed into the user's first application after sign-up; a typed answer is handed over and read by the model at that point. Services shown on the page are listed in `src/lib/services.js`.
- Documents are encrypted at rest (AES-256-GCM, `server/storageCrypto.js`) with the key in `config/secrets/storage.key` (mode 600). **Back that key up separately from `storage/`: without it no stored document can be read.** `node scripts/encrypt-storage.mjs` creates the key on first run and encrypts any plain files; it is safe to re-run.
- Password reset: "Forgot password?" on the sign-in page emails a single-use link valid for 30 minutes (only its hash is stored). Resetting signs the account out everywhere. Emails go through `server/mailer.js`: copy `config/mail.example.json` to `config/mail.json` with SMTP details to send them; until then they are kept in the `email_outbox` table (status `not_configured`) and nothing is delivered.
- Payments: the government fee is paid on the Payments page before an application is submitted. `config/payment.json` has `"mode": "test"`, a dummy checkout (UPI / card / net banking, with a switch to simulate a failure) where no money moves; `serviceFeeRupees` adds our fee if set. The server computes amounts and allows one successful payment per application.
- Security headers: CSP, anti-framing, no-sniff, referrer policy and HSTS are set in `vite.config.js` (pages) and `server/apiPlugin.js` (API).
- `./reset_all.sh` wipes all users, sessions, applications, documents and stored files.
- Brand name/domain are placeholders — edit `src/lib/brand.js` to rename.
