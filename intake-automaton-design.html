The intake automaton

1 · RationaleWhy an automaton, and not just a chatbot

The obvious way to build "an AI that tells you which licence you need" is to hand the conversation to a language model. I deliberately didn't, for four reasons.

  • The answer is the law, not an opinion. The licence type follows fixed rules: turnover thresholds, mandatory Central Licence categories, deemed registration for street vendors. A rule written as code gives the same answer every time and can be explained line by line. A model's answer can drift between runs, and a wrong licence costs the user real money and time.
  • Our users tap more than they type. A chaat-cart owner or a home baker shouldn't need to write a paragraph. Big tap cards with examples ("Kirana shop, distributor, cold storage…") work for low literacy, small screens and patchy networks.
  • A finite machine can be tested completely. The set of possible tap journeys is finite (about 17,500), so a script can walk every one of them and prove that each ends in a sensible verdict. You can't do that with a free-form chat.
  • The model still has a job, just a narrower one. It only translates free text ("cloud kitchen in Pune, about 80 lakh, we're on Swiggy") into the same facts a tap would produce. It never decides the licence.
The one-line philosophy: rules decide, taps are the main road, and the model is an interpreter at the side of the road, used only when needed and remembered once used.

The same file runs in the browser (for instant taps and the landing-page chat) and on the server (which is the source of truth), so the two can never disagree.

2 · ApproachThe shape of it

The machine's state is a small object of facts: what the business does, where it runs, how many places, which states, whether it sells online, yearly sales. Each question is a transition that fills some facts, and it declares four things:

PieceWhat it answersExample (the "place" question)
relevant(facts)Does this question apply to this business at all?Only for food businesses
answered(facts)Do we already know the answer?facts.place is set
options(facts)Which choices make sense given earlier answers?A manufacturer is never offered "cart or street stall"
apply(choice)Which facts does a tap set?"A factory" → place: 'premises'

The next question is simply the first question that is relevant and not yet answered. When none is left, the licence rules run on the facts and produce the verdict. There's no hard-coded "go to question 5" anywhere; the route emerges from the facts, which is what makes the machine easy to extend.

3 · ApproachThe questions, and why each exists

4 · ApproachChanging your mind without breaking anything

Users go back: they tap "change" on the summary, press undo, or type something that corrects an earlier answer. Because options depend on earlier answers, a change can make a later answer impossible. For example, someone picks "cart", then changes their activity to "make or pack", and a factory can't be a cart.

After every change, reconcile walks the questions and clears any answer that the current options no longer allow. The cleared question simply becomes "unanswered" again, so it's asked next. Nothing needs special-case code; the machine heals itself. The same step upgrades old saved applications to the current fact shape when they're read, which is how existing users picked up new questions without a migration.

5 · ApproachThe consistency arm

Removing impossible options isn't enough. Some combinations are possible but suspicious, and typed answers can quietly contradict taps. This arm catches three kinds of divergence and asks one friendly "Just checking" question to resolve each.

KindExampleWhat happens
ImpliedA home kitchen is one place"How many places?" isn't asked. If "several places" arrives anyway, the user picks: "Just one place: my home kitchen" or "Change where I run it".
UnlikelyHome kitchen or cart selling over ₹1.5 crore; carts in several states; a cart running a food marketplace"Is that right?" with Yes (remembered, never asked again) or Change… for each answer involved.
ContradictionTapped "restaurant", later typed "from my home kitchen""Earlier you said X, but that sounds like Y. Which is right?" If the text only adds something ("we also make pickles"), it asks "Should I add it?" instead.

The check is a real question inside the machine, placed first in the list, and relevant whenever an issue is open. So the path checker walks its branches like any other, and no journey can end with an unresolved issue.

Principle: the system never silently overwrites something the user said. It either fills a gap, or asks.

6 · ApproachReading typed answers, in layers

Typing is always allowed ("None of these? Tell me in your own words"). A typed answer passes through up to three layers and stops at the first that can answer.

  • Rules are cautious on purpose. "bakery" or "haan" or "30k a month" are answered instantly. "Cloud kitchen in Pune, 80 lakh, Swiggy" is not, because the rules would only catch "cook" and lose the city, sales and online facts. Longer sentences go to the cache or the model, which read everything.
  • The cache learns from real users. The second person to type a sentence gets the answer in about 70 ms instead of 2 s. Reordered wording still matches ("we sell on Swiggy, cloud kitchen, Pune…").
  • Versioned. Changing the prompt or the fact schema means bumping PROMPT_VERSION, and older cached readings stop being used automatically.
  • The public landing chat uses layers 1 and 2 only. Visitors without an account can never make the server call the model, so it can't be abused as a free LLM. Anything unknown is handed over after sign-up, where the model reads it and caches the result for everyone after.

7 · ApproachChecking every path

node scripts/check-intake.mjs walks every possible tap journey, including every "Just checking" branch, in about 3 seconds. For each finished journey it verifies:

  • it ends in a verdict (a licence, deemed registration, or "not needed");
  • no question repeats, except through a legitimate "change" or "back";
  • no forbidden combination is reachable: a factory on a cart, a transporter at home, a home kitchen with several places, several states for a single-state business, and a few more;
  • no journey ends with an open consistency issue;
  • mandatory Central Licence cases never get anything smaller;
  • changing any still-relevant answer always leads back into a valid journey.

Why this matters: it turned "does the flow still make sense?" from a manual click-through into a 3-second check. Every rule change since has been made with it running, and it has caught real mistakes, including a loop and a question that could never be answered.

8 · Trade-offsJudgement calls worth knowing about

A few rules are my reading of the chart plus common sense. They're easy to change, but an FSSAI expert should confirm them.

  • Airport, railway and seaport outlets are offered only to businesses that cook or sell to customers, and they always get a Central Licence (chart step 4).
  • Street carts are offered only for cooking or retail, never for manufacturing, wholesale, storage or import.
  • A home is never offered to importers, wholesalers, stores or transporters, and always counts as one place.
  • Sales between ₹12 lakh and ₹1.5 crore are one band: the 2026 rules removed the old ₹12 lakh cut-off.
  • Several places in one state currently gets one application plus a note that each place needs its own approval; the app doesn't yet create one application per place.
  • Typed facts only grow lists ("we also make pickles" adds, never removes). Removing something needs a tap or undo, which is harder to do by accident.

9 · FutureWhat I'd improve next

Roughly in the order I'd do them. now means small and valuable, soon needs a decision or some build, later is worth it once there's traffic.

Correctness and coverage

Expert review of the rule table nowWalk an FSSAI consultant through section 8 and the "unlikely" rules. Cheap, and it turns my judgement calls into confirmed rules.
Kinds of business the chart doesn't cover soonExporters and merchant exporters, 100% EOUs, health supplements and other non-specified foods, and capacity thresholds for dairy, meat and oil. Each is an option or a question plus a rule; the checker will show what it breaks.
One application per premise soonMake "several places" real: a head-office Central Licence plus one application per unit, each with its own turnover and address.
State-specific differences laterSome states ask for extra NOCs or documents. A per-state overlay on the document rules would keep the core machine national.

Making the intelligence smarter and cheaper

Let the model help write rules, offline nowThe final fact combinations are finite. Run the model once over all of them, ask it to flag implausible ones, and review its suggestions as new consistency rules. The model's judgement is captured once, and no model call is needed at run time.
Promote the cache into rules soonAnswers that keep hitting the cache ("tiffin wala", "achaar banate hain") should become lexicon phrases after a quick human look, so they need neither the cache nor the model. A small admin page listing top cache hits would make this a five-minute weekly job.
Confidence, not just yes/no laterHave the model return a confidence per fact. Low-confidence facts become a quick "Did you mean…?" confirmation instead of being accepted outright.
Hindi and regional languages laterThe machine is language-free (ids and facts); only labels and the lexicon are English/Hinglish. Translating labels plus a per-language lexicon would open it to far more users without touching the rules.

Understanding users

Per-question analytics soonRecord which question people drop off at, how often they type instead of tap, and which layer answered. That shows which questions confuse people, and how much the cache is saving.
"Why am I being asked this?" laterEach question already knows why it's relevant. A small link that says "because you sell from a cart" would build trust and cut drop-off.

Engineering hygiene

Rules as data laterThe questions and consistency rules live in JavaScript today. Moving the tables (options per activity, unlikely combinations) into a JSON file would let an expert edit them with the checker as a safety net, without touching code.
Typed-answer regression set soonA list of real typed sentences with their expected facts, replayed through the rules and cache on every change. It's the typed-answer equivalent of the path checker.
Cache privacy soonThe cache stores the normalised typed text. If people start typing names, phone numbers or addresses, skip caching answers that contain them.
